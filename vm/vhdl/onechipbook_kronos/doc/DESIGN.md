## The instruction-set gap (the crux)

`xd0.dsk` was built for the **Kronos-3 VM** (`vm/int`). Its boot chain and OS
do I/O through *M-code opcodes*, not memory-mapped registers:

| opcode | VM meaning (defCodes.d + VM.cpp)            | 5.0 FPGA microcode today |
|--------|---------------------------------------------|--------------------------|
| 0x90   | `inp(reg)` — read I/O register              | trap 7                   |
| 0x91   | `out(reg, w)` — write I/O register          | trap 7                   |
| 0x92   | io2 — disk: pops (len, adr, sec, dsk, op)   | serial byte read (!)     |
| 0x93   | io3 — putchar                               | serial byte write        |
| 0x95   | rcmp — array compare, pushes 2 addresses    | trap 7                   |
| 0x96   | wmv — word move (overlap-safe)              | old-convention INP (!)   |
| 0x97   | bmv — BitMove (5 args)                      | old-convention OUT (!)   |
| 0xEC-EE| bbu/bbp/bblt — bit-block ops                | trap 7                   |

The I/O opcode block moved between Kronos generations (see the version table in
`excelsior/src/sys/def/defCodes.d`); the 5.0 core implements an older
convention. So the microcode (`vm/vhdl/5.0/cpu/Kronos.mkas` →
`Microcode.vhdl`, rebuilt with the reimplemented assembler `mkas.py`) must be
re-targeted to the VM convention. Key facts for that work:

* `rg_io` is **hardwired to 0xFFFFF000** (DataStorage.vhdl): the top 4KB of the
  word space, `0x7F000-0x7FFFF`, is the CPU's I/O page (that's why the console
  sits at 0x7F000).
* `reg & 0xFFF` is ONE microinstruction: `x=rg_stk alu=alu_bic y=rg_io` —
  bic with the io base *is* the 12-bit mask. OR the result back with `rg_io`
  (or add — bits are disjoint) to form the I/O-page address.
* The old monitor code shows the addressing idiom: `mem_write=0x12 x_io y=5`
  writes r5 to io_base+0x12 → our disk registers live at those same offsets.

### VM semantics to honour (from vm/int/src/VM.cpp)

* **io2**: pops len(bytes), adr(word addr), sec, dsk, op; pushes 1/0.
  op 4 = read: file offset = `sec*512`, len bytes into words at adr.
  Booter reads 4KB blocks: `read(n, a, 4096)` — `REPEAT ... UNTIL ok`.
* **inp/out**: 12-bit I/O register space; console = DL11 at 0xFB8-0xFBB
  (`Console con(0xFB8, 0x0C)`; 177560b..177566b DIV 2):
  +0 RCSR bit7 rx-avail, +1 RBUF (read consumes), +2 XCSR bit7 tx-ready
  (always 1 in the VM), +3 XBUF write = transmit. Bit6 = interrupt enables.
* **wmv**: pops sz, from, to; copies backward when to>from (overlap-safe).
* **rcmp**: pops sz, adr, adr1; scans words; pushes (adr1', adr') at the
  mismatch (or sz==0 pushes adr1 twice).
* **bmv**: pops sz, i, j, a, b → BitMove(b, a, j, i, sz). Deferred — traps
  reveal usage.

## Hardware (this directory, all sim-verified at the plumbing level)

* `src/sd_disk_controller.vhdl` — owns the SD card. Auto-loads sectors 0-3 to
  word 0 after reset (replaces sd_boot_loader+bridge), then serves io2 ops via
  registers on the I/O page; DMA master writes sector data into SDRAM.
  Registers at 0x7F010+: +0 SEC, +1 ADR, +2 LEN, +3 CMD/STATUS(bit0 busy),
  +4 RESULT, +6 DSK. Ops: 1/2→ok, 3→writes DISK_4KB (=197 for xd0.dsk) to
  mem[ADR], 4→multi-sector read, 5/6→fail (read-only bring-up).
* `src/dl11_console.vhdl` — DL11 regs at I/O page 0xFB8-0xFBB + 57600 8N1
  UART on the DB9 (BAUD_DIV=373 @ 21.477 MHz). Debug taps mirror TX bytes.
* `src/OneChipBook.vhdl` — top: I/O page decode (0x7F000-0x7FFFF; unmapped
  reads ack 0), SDRAM arbiter (disk DMA gets the bus between CPU transactions),
  CPU held in reset until boot_done.
* Sim: `sim/sd_model_xd0.vhdl` serves all 1580 sectors of xd0.dsk (from
  `xd0.dec`, generated by `sim/gen_xd0_dec.py`); `sim/tb_onechip.vhdl`
  decodes the UART line and passes on the booter's "Loaded OK";
  `sim/compile_onechip.sh` builds it (sdram_model MEM_HW=1048576 backs the
  full 19-bit space — the booter's memory probe reaches 1MB).

## Boot flow

dd xd0.dsk (whole image) onto the card → controller auto-loads sectors 0-3
(the genuine two-stage loader) → CPU warm-restarts → stage-1 calls io2 to load
the booter → booter sizes memory (expects "1024KB memory" on the console),
reads SYSTEM.BOOT via io2 ("Loaded OK"), builds the OS process, TRAnsfers.

## Disk layout (MBR partitions)

The card carries a real **MBR partition table** at sector 0. At power-up
`sd_disk_controller` reads sector 0, and maps io2 unit N to the Nth primary
partition — base sector and length come from the table, so the layout lives on
the card, not in the bitstream (states `MBR_REQ/MBR_DATA/MBR_DONE/MBR_BOOT`;
the boot block is loaded from partition 1's start, not absolute sector 0).

    partition 1 → unit 0 (/dev/xd0)  Excelsior boot/root, type 0xDA
    partition 2 → unit 1 (/dev/xd1)  Excelsior,            type 0xDA
    partition 3 → unit 2 (/dev/xd2)  FAT16 exchange vol,   type 0x0E

Type 0xDA hides the Excelsior volumes from Linux; type 0x0E (FAT16-LBA) is
read/write on both Linux and Excelsior's `MSDOS.m` driver — the shared area.
`getsize4kb` now returns each partition's own `sectors/8`.

**Backward compatible:** if sector 0 has no `0xAA55` signature the controller
falls back to the legacy fixed `sector = unit<<16` map and boots from sector 0,
so a raw (un-partitioned) card still works.

Build a card image with **`mkcard.py`** (writes the MBR, drops xd0/xd1 into the
Excelsior partitions, and `mkfs.fat`s the FAT one):

    ./mkcard.py --xd0 ../../../xd0.dsk --xd1 ../../../xd1.dsk --fat-mb 128 --out card.img
    sudo dd if=card.img of=/dev/sdX bs=4M conv=fsync status=progress   # check /dev/sdX!

The parser is unit-tested by `sim/tb_mbr.vhdl` (+ `sim/gen_mbrtest.py`), which
drives the io2 register interface against a crafted MBR and checks each unit
maps to the right absolute LBA, plus getsize and out-of-range rejection.

## Simulation faithfulness — IMPORTANT

The GHDL sim substitutes `*_sim` CPU components for the real `cpu/` files
(which don't build under GHDL due to `write(ln,"literal")` overload ambiguity
in their debug-only trace blocks). A diff of real-vs-`_sim` (ignoring trace)
found they are logic-identical EXCEPT **`DataCacheFM_sim` BYPASSES the cache**
(`cache_hit0/1 <= '0'`, a leftover Tang Nano/Gowin corruption workaround).
Synthesis uses the REAL cache (the OneChipBook doesn't need the bypass), so the
cache-bypassed sim was UNFAITHFUL — it corrupted the booter's `memory_top()`
probe (the CPU collapsed into a mem[0] loop).

Fix: `sim/DataCacheFM_realcache.vhdl` = the real `DataCacheFM.vhdl` with only
its two `synthesis translate_off` trace blocks removed (all cache logic intact,
GHDL-compatible). `compile_onechip.sh` now uses it. With the real cache:
* `memory_top()` runs correctly (address range climbs 0→~62 k steadily).
* The booter reaches its console + trap handler.

## Current status (sim, faithful real-cache build, 8-sector boot)

The real Excelsior boot chain runs: `memory_top()` works, the memory-size line
prints, but read_system **traps** and the boot ROM's panic handler dumps:
```
G 000000A4 F 000000E3 PC 00000156 -> 00000000
00000000=00000090 ?01
```
then the CPU executes from address 0 (mem[0]=0x90) in a loop. The fault is a
`cl6` (call-local) whose target `mem[F+6]` computes to 0 → transfer to addr 0.

### Verified facts (each cost a slow sim run — don't re-derive)
* **Boot load is byte-correct**: SDRAM word 0 = 144, word 233 = 282, word 342 =
  0x1EAE26D6 — all match xd0.dsk (tb "BOOTLD"/controller probe).
* **The dumped F=0xE3=227 is the TRAP HANDLER's F, not the faulting F.** The
  cache never reads word 233 (DataCacheFM_realcache "CACHE233" probe: 0 hits in
  30 ms), so the faulting `cl6` reads `mem[F_fault+6]` for some OTHER F_fault —
  chasing mem[233] was a dead end. Get the faulting F from a proper trace, not
  the dump.
* **The reference VM boots the SAME disk correctly** (see below) — so the boot
  data, disk, and algorithm are fine. The divergence is in the RTL: either a
  DataCacheFM behavior (write-back/eviction/dirty) that the M3a stub never
  exercised, or a latent microcode bug in a complex opcode path (memory_top /
  read_system / the call sequence). NOTE: it is UNCONFIRMED whether the 5.0
  FPGA microcode ever actually booted the real OS on hardware — the stub is all
  that's proven — so the microcode itself is a live suspect for complex paths.

### Eliminations (each proven by an identical trap, don't re-test)
* **The CPU core is NOT the bug.** A 100%-REAL core (real Decode /
  InstructionCache / DataStorage / Kronos with only trace stripped, in
  sim/real_*.vhdl, + DataCacheFM_realcache) traps IDENTICALLY to the *_sim
  build. So the *_sim stand-ins are faithful and the real core (proven to boot
  the OS on Spartan-3 per user photos) reproduces the fault. Build: analyze
  real_Decode/real_InstructionCache/real_DataStorage/real_Kronos instead of the
  *_sim ones (all entity names match; they're drop-in).

* **The SDRAM controller is NOT the bug.** Swapping it for sim/ideal_memory.vhdl
  (a flat 1-cycle SRAM-like memory, drop-in for the sdram_controller entity)
  produces the IDENTICAL trap (`... PC 00000156 -> 0`, same panic, same mem[0]
  loop). So the fault is deterministic and memory-timing-independent — not the
  SDRAM controller, cache-vs-SDRAM coherence, or read latency. Build it with the
  same compile as compile_onechip.sh but analyze ideal_memory.vhdl in place
  of sdram_controller.vhdl (probes must use to_integer(SIGNED(..)) — data words
  have bit 31 set and overflow unsigned->integer).
* **Boot register setup matches the VM.** vm/int RestoreRegisters (VM.cpp) does
  P=mem[0], G=mem[P], F=mem[G], L=mem[P+1], PC=mem[P+2], M/S/H=mem[P+3..5] —
  identical to the microcode rs_mode="01". (The VM also does H-=AStackSize+1 +
  RestoreAStack, but that's for its SOFTWARE expr-stack; the FPGA uses hardware
  stack regs, so N/A.)

### The fault is in memory_top's probe loop (golden VM trace obtained)
The reference VM boots (`vm/int/build-release`, built -DKTRACE, traces PC/IR/
regs to stderr; `kronos_vm xd0.dsk xd1.dsk 2>trace`). Decoded:
* Boot: F=434 stage-1 → CF → ... → **memory_top is the procedure at F=227**.
* **PC is a BYTE offset from F**, not a word address — my earlier "cl6 at word
  342" was WRONG. Trap PC=0x156=342 is byte 342 from F=227 = the memory_top
  loop's **NEQ (0xA5)** comparison. The loop (bytes 321-361): MOVE fill, li4
  pattern, ssw0 (write mem[a]), lsw0 (read mem[a]), **NEQ** (readback != pattern),
  NOT, jzf (exit if differs), a+=bank, repeat. The VM runs it 16× (16×64K =
  4 MB) then the 17th read is OutOfRange → exits → "4096KB memory".
* My RTL faults on ~the FIRST iteration (range reaches 65493 = one 64K bank,
  then collapses). So the write/read/compare of the probe word faults where the
  VM succeeds. The trap "-> 00000000" is the boot's panic handler.
* One concrete VM-vs-RTL delta seen in the trace: **H=917 in the VM vs 933 in my
  RTL** (the VM does H-=AStackSize+1 for its software expr-stack; the FPGA uses
  hardware stack regs). Probably benign (higher H = more permissive) but not yet
  ruled out.

### Deeper isolation (2026-07-16, second pass) — the collapse is NOT a trap
Using the reference-VM golden trace + a ring-buffer probe in tb_onechip
(dumps the last 48 CPU accesses on a high→0 address jump) and a trap probe in
sim/real_Kronos.vhdl (reports trap_mem/sh/stk):
* **No hardware trap fires** (trap_mem/sh/stk stay 0 through the collapse). So
  the jump to addr 0 is a SOFTWARE control transfer, not a CPU trap.
* The "panic" text `... PC 00000156 -> 00000000` written to 0x7F000 IS real (the
  boot's diagnostic), and PC byte-342 from F=227 = memory_top's NEQ compare.
* The collapse happens right after memory_top's FIRST heavy write burst — the
  initial fill `move(S,0,bank-S)` copies mem[0..] to mem[453..65535]; the cache
  writes complete to word 65535, then the CPU jumps to 0 BEFORE the next probe
  write (no cache write at 65536). So it's the transition after a ~65K-word
  write burst — the first time the cache's write/flush path is exercised hard
  (the M2/M3 stub only ever did cache READS).
* Fixed a real sim bug along the way: DataCacheFM's `base` register has no reset;
  GHDL leaves it 'U' → tlb_off=0 → spurious TLB behavior. Initialised to 0 in
  DataCacheFM_realcache (Altera powers regs to 0, so HW was fine). Did NOT change
  the collapse, but is correct.
* MOVE direction ruled out: both the VM (VM.cpp 0xC0: mem[i++]=mem[j++]) and the
  microcode copy FORWARD, so the overlapping fill produces identical content.

Since the OS demonstrably boots on Spartan-3 (real cache, real MOVE, real
memory_top), this is SIM-SPECIFIC: most likely another uninitialised register in
the real cache/fetch path that GHDL leaves 'U' but Altera powers to 0, exposed
only by the write-heavy memory_top. NEXT: hunt uninitialised signals in
DataCacheFM/InstructionCache/DataStorage (grep `signal .*std_logic` without
`:=`), or capture the instruction-fetch (I-cache) address/data right at the
jump-to-0 to see if the fetch returns a corrupt opcode after the write burst.

### Iteration 4 (2026-07-16) — opcode trace pins the exact transition
Captured the RTL's executed-opcode stream at the collapse (probe in real_Decode
at cmd_end, gated to the window; run with --ieee-asserts=disable to survive the
metavalue flood). Result: after memory_top's initial bank-fill MOVE completes
(cache writes reach word 65535), the CPU executes exactly ONE `li4` (0x12), then
the instruction fetch STALLS ~25 us and resolves to address 0 (then loops on
mem[0]=0x00). The reference VM does `li4` then `slw4` (0x34) and continues. So
the divergence is the instruction FETCH immediately after that li4 — the fetch
address (InstructionCache: a_bus = f + pc/4) drops to 0.

MORE eliminations this iteration (all reproduce the identical collapse — word
65172 @19.985ms):
- Initialised EVERY signal in ALL 5 real CPU files to 0 (not just base) → no
  change. So it's NOT 'X'/uninitialised-register propagation, despite a
  persistent metavalue warning flood (that flood comes from the tb's numeric_std
  probes / a non-CPU source, not the fault).
- BlockRam_sim write-first vs read-first → no change. So it's NOT the cache RAM
  read-during-write semantics (Xilinx-vs-Altera hypothesis disproved).
- The register file (src/DistrRam.vhdl) is already init 0.

So the fault is a deterministic instruction-fetch corruption right after the
first heavy write burst, reproducing with the real core + defined signals + both
memory models + both BlockRam modes. This is at the limit of what black-box sim
probing reveals. NEXT: expose the InstructionCache f/pc/pc_new/write_f every
cycle across the li4→fetch transition (the earlier attempt didn't fire because
the CPU is stalled — gate on the clock only, no stall/cmd_end condition, tight

### Iteration 5 (2026-07-16) — it's a panic-handler HANG, not corruption/deadlock
Deep probing at the collapse (fetch ring in real_InstructionCache; Wishbone bus
probe in the tb; write logging in ideal_memory). Corrected/definitive picture:
* **The boot load is CORRECT.** mem[312] = 0xAEA51234 = the disk value exactly
  (an earlier "code corruption" claim was a hex-conversion mistake on my part;
  every boot-DMA write to words 305-320 matches the disk). memory_top does NOT
  write the code region (0 writes to 300-320 post-boot).
* **The CPU is NOT deadlocked and does NOT trap.** The Wishbone bus at the
  collapse shows the CPU actively WRITING bytes to 0x7F000 (the memory-mapped
  console) in a repeating pattern = a panic/diagnostic routine printing
  "G 000000A4 F 000000E3 PC 00000156 -> 00000000" over and over (a HANG in that
  routine). No trap_mem/sh/stk fires.
* The InstructionCache pc_r is frozen at 342 (=byte 342 from F=227, memory_top's
  NEQ) with d_bus=0 only because the fetch is idle while the panic routine does
  data writes — NOT a stuck fetch.

So: memory_top runs, then the boot code BRANCHES (in software) to a
panic/diagnostic printer that hangs looping. The trigger is a software decision
in the boot code, not a hardware fault. NEXT: capture the executed-opcode +
PC-jump stream through the memory_top→panic transition (a jump/call target, or a
comparison result) and compare with the reference VM at the same point — the VM
takes a different branch there. The panic string format ("G .. F .. PC .. -> ..")
should be findable in the boot code / excelsior sources to identify the routine
and what calls it.

### Iteration 6 (2026-07-16) — ROOT CAUSE: cache serves hit=1 with data=0 for code
Traced the exact "branch." It is NOT a software branch — the CPU executes ZEROS:
* PC trajectory after the MOVE: the li4 at pc=322 decodes (op=0x12), but every
  fetched byte from pc=323 on reads 0 (the li4 immediate at pc=325 should be 0x01,
  reads 0; pc=327+ = slw4/etc. all read 0x00=li0). So the instruction fetch of the
  memory_top code (words 307+) returns 0.
* Cache probe on the instruction port (a1) for words 305-317: **cache_hit1='1'
  (valid tag, key match, no collision) but do1_data=0** for words 309-313. The
  cache has VALID TAGS but ZERO DATA for the code. (Word 308: miss, and the refill
  data register still holds word 307 = an off-by-one/stale refill too.)
* MEMORY holds the code correctly (mem[307..317] = disk). So the shared I/D
  DataCache's DATA store is zeroed for the code lines while the TAG store still
  says valid+matching -> the fetch "hits" and returns 0x00.
* Mechanism: the MOVE writes mem[453..65535] via the data port (a0). Those
  addresses ALIAS the code lines in the direct-mapped 512-entry cache (e.g. word
  821 -> index 309, same as word 309). The write updates the tag/valid (and/or the
  dual-port BlockRam read-during-write) but leaves the DATA store 0 for the
  instruction port -> tag/data inconsistency. So the CPU fetches 0x00 for the code,
  runs li0 garbage to pc=342, and falls into the panic printer that hangs.
* Sim-specific: the OS boots on Spartan-3 with the same cache, so the real
  Xilinx/Altera dual-port BSRAM does NOT exhibit this. The bug is in how
  BlockRam_sim / the DataCache tag-vs-data update behaves in GHDL.

NEXT: find the DataCache FSM path that updates the key/valid BlockRam but not the
data BlockRam for an aliasing write (the `a0_write1 and (tlb_hit0=0 or
tlb_data0(tlb_tag_ce)=1)` case, ~line 469, updates only dirty/valid/key/error),
or the cross-port (a0 write / a1 read) read-during-write in BlockRam_sim. Probe
we0dat vs we0key and di1_data on the refill of word 309, and check the dual-port
same-index write/read behaviour. Fixing the BlockRam model or that FSM case
should let the code fetch return real data and the boot proceed.

### Console is MEMORY-MAPPED at 0x7F000 (not the DL11!)

The real boot chain writes console output by STORING bytes to word 0x7F000
(like the bring-up stub), NOT via inp/out to the DL11. Confirmed in sim: the
booter blasts ASCII to 0x7F000. `OneChipBook` now steers 0x7F000 writes into
the DL11 XBUF → UART (`con_stb`/`con_reg`), so console output reaches the serial
port on hardware; the DL11 inp/out registers (0xFB8-0xFBB) still work for code
that uses them. The io0/io1/io2/io3 microcode + DL11 remain correct and needed
(the OS proper and the io2 disk path use them).
